# Publishing a release

Fresh as of 2026-09-08. A release tag lands on a commit whose docs already state the release,
and pushing the tag is the release: no token exists anywhere.

## One version

`visaphoto/__init__.py` holds `__version__`; `pyproject.toml` reads it (`dynamic = ["version"]`);
`.claude-plugin/plugin.json` names the same string (the plugin's own manifest is what Claude
Code reads, so it is not repeated in `marketplace.json`). `tests/test_version.py` fails when the
CHANGELOG, the README, the plugin manifest or the skill disagree with `__version__`, and the
publish workflow refuses a tag that does not name it.

## How publishing works

`.github/workflows/publish.yml` runs on a pushed tag `v<version>`:

1. `build`: checks that the tag names `__version__`, runs the tests, runs
   `tools/release_check.sh` (builds the wheel with `uv build`, installs it into a fresh
   environment outside the checkout, runs `visa-photo --list-specs`, checks the wheel's
   metadata header and version), and keeps `dist/` as the artifact.
2. `publish`: waits for the `pypi` environment's required reviewer, then uploads that artifact
   to PyPI with `pypa/gh-action-pypi-publish` through **trusted publishing**: GitHub gives the
   job a short-lived OIDC identity (`id-token: write`) and PyPI, which is configured to trust
   owner `dweekly`, repository `visa-photo`, workflow `publish.yml`, environment `pypi`,
   exchanges it for a single-use upload token. PEP 740 attestations are generated by default.

A manual run (`workflow_dispatch`) rehearses the same build on TestPyPI, through a second
trusted publisher configured on test.pypi.org for environment `testpypi`.

## Checklist

1. `CHANGELOG.md`: move the unreleased sections under `## <version> - <date>`.
2. `README.md`: the status line names the version and what each profile does.
3. `__version__` and `plugin.json` bumped; `pytest` green, including `test_version.py`.
4. Commit, review, merge.
5. Rehearse: `gh workflow run publish.yml` and check https://test.pypi.org/project/visa-photo/
   renders the README and the metadata. TestPyPI is not permanent storage.
6. Tag the merge commit: `git tag -a v<version> -m "<version>" && git push origin v<version>`.
   Approve the `pypi` environment when the workflow asks. A filename uploaded to PyPI can
   never be replaced: get the metadata right before this step, not after.
7. Smoke test from a machine that has never seen the repo:
   `uvx --python 3.12 visa-photo --list-specs`, then `--fetch-models` and one real photo.
8. GitHub release notes: `gh release create v<version> --notes-file` with the CHANGELOG section.

## What the wheel's metadata should say

`License-Expression: MIT` and `License-File: LICENSE` (PEP 639, via `license = "MIT"` and
`license-files` in `pyproject.toml`; no licence classifier), `Author-email`, `Requires-Python`,
Python-version and operating-system classifiers, `Description-Content-Type: text/markdown`, and
the `Project-URL` set. `tools/release_check.sh` prints the header and fails on a licence
classifier.

## The plugin

Users add the repository as a marketplace and install the plugin from it:

```sh
claude plugin marketplace add dweekly/visa-photo
claude plugin install visa-photo@visa-photo
```

Before merging a change to the skill, install it from a clean Claude configuration
(`CLAUDE_CONFIG_DIR` pointing at an empty directory) with the local path as the marketplace
source, and confirm the skill is listed.
